---
title: Schema from your models
description: Describe your tables once, in the structs of your code, and let Gonestly write and apply the SQL migrations when they change.
---

You do not have to write SQL to change your database. The structs with `db` tags are the schema. Change one, run `gonestly migrate dev`, and the migration is written for your database, with the SQL that undoes it, and applied.

> [!NOTE]
> Schema migrations are available from version 0.5.0. Migrations that you write by hand keep working next to them.

## The workflow

```go title="internal/tracks/model.go"
type Track struct {
	ID     int64  `db:"id"`
	Title  string `db:"title"`
	Artist string `db:"artist" schema:"index"`
}
```

```sh
gonestly migrate dev
```

```text
• create_tracks:
  create the table tracks
✓ created migrations/20260401120000_create_tracks.up.sql
✓ created migrations/20260401120000_create_tracks.down.sql
✓ applied 20260401120000_create_tracks
```

Later you add `Slug *string` to the struct and run the same command. Only the difference is written:

```sql
ALTER TABLE tracks ADD COLUMN slug VARCHAR(255);
```

`gonestly generate resource` uses the same machinery: it writes the model, and the migration that creates its table.

| Command                              | What it does                                                       |
| ------------------------------------ | ------------------------------------------------------------------ |
| `gonestly migrate dev`               | Writes the migration for the changes in your models and applies it |
| `gonestly migrate dev --create-only` | Writes it and leaves applying it to `gonestly migrate up`          |
| `gonestly migrate diff`              | Shows the SQL without writing anything                             |
| `gonestly migrate baseline`          | Adopts migrations that you wrote by hand; see below                |

`--name add_slug` names the migration; otherwise the name is made from the changes.

## What a model describes

A model is an exported struct with at least one `db` tag, the same structs that `gonestly generate columns` reads. Embedded structs, such as a shared `Base`, are part of the table. The table is named by the `TableName` method, which has to return a string literal, or else the plural of the type name in snake case: `Product` is `products`.

The Go type decides the column:

| Go type                            | PostgreSQL                 | MySQL             | SQLite      |
| ---------------------------------- | -------------------------- | ----------------- | ----------- |
| `int64`, `int`, `uint64`, `uint32` | `BIGINT`                   | `BIGINT`          | `INTEGER`   |
| `int32`, `uint16`                  | `INTEGER`                  | `INT`             | `INTEGER`   |
| `int16`, `int8`, `uint8`           | `SMALLINT`                 | `SMALLINT`        | `INTEGER`   |
| `string`                           | `VARCHAR(255)`             | `VARCHAR(255)`    | `TEXT`      |
| `bool`                             | `BOOLEAN`                  | `BOOLEAN`         | `BOOLEAN`   |
| `float64`, `float32`               | `DOUBLE PRECISION`, `REAL` | `DOUBLE`, `FLOAT` | `REAL`      |
| `time.Time`                        | `TIMESTAMPTZ`              | `DATETIME(6)`     | `TIMESTAMP` |
| `[]byte`                           | `BYTEA`                    | `LONGBLOB`        | `BLOB`      |
| `json.RawMessage`, slices and maps | `JSONB`                    | `JSON`            | `TEXT`      |

A pointer, or `sql.NullString` and its relatives, makes the column optional; everything else is `NOT NULL`. A named type such as `type Status string` is read through to its underlying type. A field named `ID`, or tagged `db:",pk"`, is the primary key, and an integer key is generated by the database unless you add `noauto`. Several keys make a composite key.

## The schema tag

Everything the Go type cannot say goes in a `schema` tag, with options separated by commas:

```go
type Track struct {
	ID       int64     `db:"id"`
	Title    string    `db:"title" schema:"size=200"`
	Slug     string    `db:"slug" schema:"unique"`
	Artist   string    `db:"artist" schema:"index"`
	Body     string    `db:"body" schema:"type=text"`
	Price    string    `db:"price" schema:"type=decimal(10,2)"`
	Plays    int64     `db:"plays" schema:"default=0"`
	Public   bool      `db:"public" schema:"default=true"`
	Created  time.Time `db:"created_at,default"`
}
```

| Option                      | Meaning                                                                                                    |
| --------------------------- | ---------------------------------------------------------------------------------------------------------- |
| `size=200`                  | Length of a string column; 255 without it.                                                                 |
| `type=...`                  | `text`, `json`, `uuid`, `bytes`, `decimal(p,s)`, `varchar(n)`, or any SQL type, used as written.           |
| `unique`                    | A unique index on the column.                                                                              |
| `index`                     | An index on the column.                                                                                    |
| `unique=name`, `index=name` | Fields that share a name make one index over all of them, in field order.                                  |
| `default=...`               | The value when an insert leaves the column out: `now`, `true`, `false`, a number, `'text'`, or `expr:SQL`. |
| `noauto`                    | An integer key that you set yourself.                                                                      |
| `onDelete=...`              | On a relation field: `cascade`, `restrict`, `setnull` or `noaction`.                                       |

A `time.Time` with `db:",default"` gets `default=now` by itself.

## Relations become foreign keys

The [relations](relations) you declare with `rel` are also the foreign keys. The key goes in the table that holds the column, and points at the primary key of the other:

```go
type Post struct {
	ID       int64   `db:"id"`
	AuthorID int64   `db:"author_id"`
	Author   *User   `rel:"author_id" schema:"onDelete=cascade"`
}
```

```sql
CONSTRAINT posts_author_id_fkey FOREIGN KEY (author_id) REFERENCES users (id) ON DELETE CASCADE
```

Declare it on either side, or both: it is one key. `onDelete=setnull` needs an optional column, which Gonestly checks.

## Renames keep your data

A field that disappears while another of the same type appears looks like a rename, and a migration that drops one column and adds another loses the data. So the command asks:

```text
? Did you rename column tracks.name to title? (y/N)
```

Without a terminal, such as in a script, say it with a flag, for a column or a table:

```sh
gonestly migrate dev --rename tracks.name=title --rename old_tracks=tracks
```

## Changes that need your say

A migration that deletes data, such as dropping a table or a column, or shrinking a column, is not written until you accept it. In a terminal the command asks; elsewhere pass `--accept-data-loss`. The SQL of an `--create-only` run is only written, so it is not asked.

Some changes only fail on tables whose rows do not fit them: a new required column without a default, a column that becomes required, a new unique index. They are shown as warnings. The migration runs in a transaction, so a failure leaves the database as it was. Give the column a default, or make the field a pointer, to avoid it.

Changing a primary key, or whether it is generated, is not written for you; write that migration by hand with `gonestly migrate create`.

## Undoing

Every migration has a `down` file, made from the same difference the other way round. A dropped column comes back empty and optional, because its data cannot come back.

## SQLite

SQLite can only add a column and little else, so for most changes Gonestly makes the table again: it creates the new table, copies the rows, drops the old one and renames the new one. The migration says `-- gonestly:foreign-keys-off`, so that the tables that point at it keep their rows (without it, dropping the table would cascade). The foreign keys are checked at the end, and the migration fails when it left a row that violates one.

## Adopting a project with hand-written migrations

A project whose migrations were written by hand does not know what schema they made, so `gonestly migrate dev` stops. When the database matches your models, tell it:

```sh
gonestly migrate baseline
```

This records the models as the schema, without writing a migration. From then on `migrate dev` writes only what changes. `gonestly generate resource` does this by itself, for the models that exist at that moment.

## The snapshot

The schema that the migrations made is kept in `migrations/schema.snapshot.json`. Commit it with the migrations: it is how the next `gonestly migrate dev` knows the difference, and it is the same for every database, so you can change from SQLite to PostgreSQL later. It is not read by the application.
